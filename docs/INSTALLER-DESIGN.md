# All-in-one installer design

[Documentation index](README.md) · [Deployment](DEPLOYMENT.md) · [Engineering](ENGINEERING.md)

## Behavior and compatibility

The entry scripts prepare missing bootstrap prerequisites and resolve `CAMPIX_REF` to one detached commit. They use a fresh source directory and never replace a checkout. The Python installer requires a clean committed source checkout and inventories the operating system, architecture, board, camera nodes, and existing installation before applying a platform-specific plan. `--dry-run` performs no installation, download, privilege escalation, or application-state changes. A downloaded bootstrap's dry run reports bootstrap requirements without fetching source; a local bootstrap delegates to the local Python installer when available.

Debian-family hosts use a target-native package, system Python 3.11 or newer, and a running systemd host. Raspberry Pi CSI keeps distribution-provided Picamera2, libcamera, NumPy, Pillow, and OpenCV together. Other supported package-manager profiles use a private, locked environment with user-owned configuration and data. Portable Linux requires an active systemd user manager, macOS a GUI LaunchAgent session, and Windows a limited user scheduled task. Windows registers Plug and Play webcams listed by FFmpeg's DirectShow input; macOS supports network cameras. Neither host offers the local CSI/V4L2 paths. Package-manager availability is an installation profile, not physical hardware qualification.

Root/elevated administrator invocation is rejected. Only explicit commands requiring system changes use elevation. Runtime remains unprivileged, the initial listener is loopback, passwords are read privately, and synthetic sources require explicit demo mode. uv 0.13.0 and optional MediaMTX v1.21.2 are version-pinned and checksum-verified. Local physical cameras are registered only from observed capture capabilities or, on Windows, from FFmpeg's DirectShow list of Plug and Play video devices. Discovery does not open a capture stream. Registration uses conservative starting profiles at 10 fps: 1280×720 for DirectShow webcams and 640×480 for board-attached cameras. It never overwrites existing profiles.

Unknown CSI sensors and vendor drivers cannot be identified from a board name. The installer reports missing packages, firmware, permissions, or unidentified devices without executing vendor scripts, guessing device-tree overlays, performing a distribution upgrade, or enabling hardware encoding. On the native Pi profile, an identified IMX500 adds the distribution firmware package `imx500-all` and a reboot recommendation; AI inference remains unimplemented. `auto` remains software `libx264`.

## Failure and recovery

Unsupported platforms and unsuitable native Python versions fail before application installation. Download, checksum, package, account-bootstrap, and startup failures return nonzero with an actionable command or requirement. No default account is created; `--non-interactive` cannot create a fresh deployment. New service activation follows successful admin setup and dependency validation. Occupied ports are rejected; startup additionally requires managed process state and a local HTTP response matching that process's PID. Those checks cannot certify camera frames or media publishing. Portable background startup uses the installed JSON configuration and ignores ambient `CAMPIX_` environment variables. The Windows background service opens no console windows: its MediaMTX and FFmpeg children start windowless and share a kill-on-close job with the service, so a crashed or killed service cannot leave hidden children holding the managed ports. A refused job is logged as a warning rather than stopping the service.

Existing accounts, configuration, media, and legacy installations remain intact. Existing deployment/state targets and startup definitions are rejected with backup/update guidance. Shared system dependencies are not automatically removed on failure. Bootstrap source staging and partially prepared portable releases can remain for diagnosis, while the Python installer's temporary build directory is cleaned up. The installer does not recursively remove user-selected paths. A failed startup is stopped/disabled where its managed profile supports that action, while its definition and application data remain available for review.

## Acceptance evidence

Regression tests cover platform/board selection, unsupported native environments, checksum rejection, failed commands, managed path bounds, existing state, account bootstrap, multi-camera deduplication, metadata/M2M node exclusion, maximum camera count, truthful empty discovery, startup/HTTP process ownership, windowless service children, and Windows child containment after abrupt service termination. DirectShow tests cover both FFmpeg device-list formats, Plug and Play-only registration, distinct sources for identical models, device-list injection, bounded and timed-out listing, native-size listing and enforcement, the padded fallback capture modes, and restart of a stalled stream. Host fixtures and mocked package/startup operations do not demonstrate a completed target-host installation. Packaging acceptance requires a wheel and installed-package smoke test; Linux package/systemd and physical-camera results are reported separately from host-only tests in [release readiness](RELEASE-READINESS.md#all-in-one-installer-verification--12-october-2026).

## Rollback

Before updating an existing deployment, stop its service and keep a consistent private database/media backup plus the previous package/configuration. Removing a new native package retains application state. Private portable environments can be replaced without deleting the stable data directory. Restoring a previous version requires a matching database backup if the schema changed. Automatic OS-package rollback, host-driver replacement, and deployment migration are outside the installer contract.
